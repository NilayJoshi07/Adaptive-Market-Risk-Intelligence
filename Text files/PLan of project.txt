# 4. The project explicitly controls look-ahead bias

We established strict information-set rules.

The basic rule is:

> A forecast for date **t** may only use information available **before the return on date t is observed**.

This was checked across the forecasting system.

### Historical volatility

The final Historical 20D predictor uses:

```python
rolling(20).std().shift(1)
```

rather than the contemporaneous rolling value.

### India VIX

India VIX was aligned using the **previous available observation**, excluding exact-date matches.

Therefore:

> Today's NIFTY return cannot leak into the VIX predictor used to forecast today's volatility.

### Expanding OLS

For forecast date `t`:

```text
Use observations < t
        ↓
Estimate coefficients
        ↓
Forecast t
        ↓
Observe actual t
        ↓
Add t to calibration history
```

This was explicitly audited.

### Overall result

**Information-set / look-ahead audit: PASS.**

# 6. GARCH-t methodology was validated

The GARCH-t model was estimated using only the pre-OOS training sample:

* **2018-01-03 to 2023-12-29**
* **1,476 observations**
* Student's t innovations

Estimated parameters included:

* μ ≈ **0.099554**
* ω ≈ **0.026594**
* α ≈ **0.096810**
* β ≈ **0.877078**
* ν ≈ **7.542749**

The parameters were then kept fixed during the OOS period while the conditional variance state was recursively updated.

Therefore the correct description is:

> A GARCH(1,1) model with Student's t innovations was estimated once using the pre-OOS training sample, and one-step-ahead forecasts were recursively generated through the untouched OOS period.

It is **not** a daily re-estimated GARCH model.

Therefore the corrected GJR recursive implementation passed the integrity test.

## The key principle from now on

**We are no longer trying to make the project "more sophisticated."**

We are trying to make it **more useful**.

Every new component should answer:

> **Who would use this? What decision does it improve? How does that decision create financial value? How can we measure that value?**

If a proposed feature doesn't answer those questions, we don't add it.

### So our immediate next step is **not coding yet**.

We should first design the **business use case and economic mechanism** properly. Once that's fixed, we can build the business-impact layer on top of your already-validated forecasting engine without disturbing the research.

Yes. At this stage, **do not add SQL, Power BI, or ML just to make the project look more “Data Science.”** Each should enter only where it solves a genuine business problem.

Your next step should be to turn the completed research engine into a **business decision system**, and then decide where SQL, ML, and Power BI naturally fit.

### Recommended roadmap

**1. Freeze the research engine — first**

Your existing pipeline becomes:

That is your analytical foundation.

**2. Define the business problem**

Business question:

Then SQL can answer actual business questions:

```sql
-- How did the portfolio perform during high-risk regimes?
SELECT
    risk_regime,
    AVG(portfolio_return),
    AVG(drawdown)
```

Or:

> How much drawdown occurred during those periods?

That makes SQL **business analytics**, rather than a decorative SQL section.

# Where Machine Learning fits

This needs more discipline.

### You do NOT currently need ML for volatility forecasting.

You already have:

* Historical volatility
* EWMA
* GARCH
* GJR-GARCH
* EGARCH
* India VIX enhancement

Adding XGBoost simply because “DS projects should have ML” would actually weaken the story.

Instead, there is one ML problem that genuinely makes sense:

## Predict the probability of a future high-volatility regime

For example:

```text
Inputs available today
        ↓
NIFTY returns
India VIX
recent volatility
volatility trend
return momentum
VIX change
rolling statistics
        ↓
ML model
        ↓
Probability of HIGH/EXTREME volatility
```

Target could be:

> Will tomorrow/next few days enter a predefined high-volatility regime?

Then compare something simple and interpretable first:

**Logistic Regression**

against perhaps:

**Random Forest / XGBoost**

The ML model should not replace your existing volatility model automatically.

Instead:

```text
Statistical Forecast
        +
ML Regime Probability
        ↓
Risk Decision Engine
```

That gives you a legitimate reason for ML:

> **The statistical models estimate expected volatility, while ML estimates the probability that the market will transition into a high-risk regime.**

That's a much stronger interview explanation than:

> “I used XGBoost because I wanted to add machine learning.”
