# Part 1 — Understanding Steps 01–05

We'll study these five scripts in order. The goal isn't just to memorize their names; it's to understand what problem each solves and why the next script exists.

## Step 01 — `01_load_market_daily.py`

Data ingestion

Purpose: Load the cleaned NIFTY 50 price data and India VIX data into DuckDB as one reusable market dataset.

### A. What goes into it?

The code reads two CSV files from your project's `data\processed` folder:

| Input                                             | Expected columns                     | Expected observations |
| ------------------------------------------------- | ------------------------------------ | --------------------- |
| `nifty50_prices_clean.csv`                        | Date, Open, High, Low, Close, Volume | 2,150                 |
| `india_vix_clean_daily_2018-01-01_2026-09-22.csv` | Date, India_VIX                      | 2,135                 |

The script requires exact column names and checks that the dates, values and market-price relationships are valid.

For example, it checks that the daily high is at least as high as the open and close, and the low is no higher than either. Those are basic market-data integrity checks.

### B. Why combine NIFTY and India VIX?

NIFTY price data describes how the market moved. India VIX is a measure of the market's expected volatility.

The script joins them by `Date`, using NIFTY's trading dates as the base. In database terminology, this is a left join.

NIFTY daily prices

2,150 dates

Left join on Date

`market_daily`

2,150 rows, with India VIX where available

The script expects 17 NIFTY trading dates without a same-date VIX observation. It retains those rows with a missing VIX value rather than filling the gap artificially.

This is important: a missing value is not the same as zero volatility. Later scripts must handle missing VIX values deliberately.

### C. What happens inside DuckDB?

The script:

1. Locates the project root and imports the shared database path.
2. Reads and validates the two CSV files.
3. Joins the datasets and renames price columns to `NIFTY_Open`, `NIFTY_High`, and so on.
4. Creates the `market_daily` table if it doesn't exist.
5. Loads the data only if the table is empty.
6. If the table already contains 2,150 rows, it does not reload it.
7. If it contains a different nonzero row count, it stops instead of modifying the database.
8. Reads the stored values back and compares them with the prepared source data.

The table has a primary key on `Date`, which prevents duplicate dates in the database.

### D. What does Step 01 produce?

The main output is the DuckDB table:

`market_daily`

It contains:

- `Date`
- `NIFTY_Open`
- `NIFTY_High`
- `NIFTY_Low`
- `NIFTY_Close`
- `NIFTY_Volume`
- `India_VIX`

The script also prints a summary of row counts, date ranges and missing VIX observations.

Why it matters: later business-evaluation scripts can query one consistent market table instead of independently reopening and joining the raw CSVs.

One limitation to understand: the script's loading decision is based primarily on row count. If a pre-existing table has 2,150 rows but contains incorrect values, it will not reload it automatically; the reconciliation checks should detect the mismatch and stop. This is safer than silently overwriting data, but it means a mismatch requires deliberate investigation.

Research ingestion

Purpose: Put the frozen research outputs into DuckDB so the business scripts can use them without relying on variables left in a notebook's kernel.

This is the bridge between your modelling work and the business-decision system.

### A. What does it read?

The script reads four research artifacts from the configured `RESEARCH_OUTPUT_V1` directory:

- `model_performance.csv` — the model-comparison metrics.
- `research_metadata.json` — the research version, asset, forecast target and data-quality declarations.
- `output_manifest.json` — the expected research version and inventory of the source outputs.

It expects exactly 673 forecast observations and 8 model-performance records, all belonging to research version `v1`.

The eight models are:

1. `Historical_20D`
2. `EWMA`
3. `GARCH_t`
4. `GJR_GARCH_t`
5. `EGARCH_t`
6. `Historical_20D_VIX`
7. `EWMA_VIX`
8. `EGARCH_t_VIX`

The metadata also declares the target as Next-day volatility and the information set as Strict pre-return information set. The script checks these declarations; it does not recreate the forecasts or independently prove that the modelling methodology is valid.

### B. What does it check before loading?

It checks that:

- Required files exist.
- Forecast columns appear in the exact expected order.
- Dates are valid, unique and chronological.
- Forecast values contain no missing or non-finite numbers.
- Model-performance columns and model order match the expected contract.
- Metadata and manifest identify version `v1`.
- The metadata declares no missing values, duplicate dates or non-finite values.

This protects the database from obviously malformed or mismatched research artifacts.

### C. Which database tables does it create?

`research_oos_forecasts`

673 rows expected · One record per date and research version

Contains the NIFTY log return, actual volatility, pre-return India VIX, eight forecast-model columns, and metadata identifying the research version, asset and forecast target.

`research_model_performance`

8 rows expected · One record per model and research version

Contains the model name, MAE, RMSE, sample size, out-of-sample start/end dates and research metadata.

The script creates each table if it doesn't exist. It loads `v1` only when both corresponding version-specific tables have no `v1` records. If the expected counts already exist, it skips reloading; if only partial data exists, it stops rather than overwriting it.

### D. An important limitation in its reconciliation

The script checks the database row counts and missing forecast values, then compares selected fields from the first and last forecast records with the source CSV.

That is useful, but it is not a full row-by-row comparison of every stored research value against the original source. In contrast, Step 01 compares the entire prepared market dataset with the database.

This doesn't prove that Step 02 loaded incorrect data; it means the script's reconciliation is narrower than a full-data integrity comparison.

Output: the two research tables in the same DuckDB database that Step 01 created or opened.

Why Step 02 matters: it makes your frozen research results available through durable database tables, independently of the notebook's in-memory state.

### Why is this a separate script?

A loading script and a validation script serve different purposes:

- Step 02 is responsible for preparing and inserting research records.
- Step 03 checks the database contract without changing the database.

If Step 02 prints `INGESTION STATUS: PASS`, that means its own checks passed. Step 03 provides a separate validation run that is useful after a kernel restart, after a database change, or before downstream scripts consume the data.

### What does Step 03 not prove?

It does not independently recompute the research models or verify that the financial forecasting methodology is correct. It verifies the declared database contract: expected tables, schemas, counts, dates, versions and required fields.

Output: a validation result in the terminal. It does not generate a new business report or intentionally modify the database.

## Step 04 — `04_test_database_recovery.py`

Restart and recovery test

Purpose: Prove that the essential datasets can be recovered from DuckDB in a fresh Python process, without depending on variables that existed in a previous notebook kernel.

This is particularly relevant to the kernel-reset problem you were solving earlier.

### What does the script do?

It opens the database using:

```
con = duckdb.connect(    str(DATABASE_PATH),    read_only=True)
```

Then it runs three queries:

1. Recovers all 2,150 rows from `market_daily`.
2. Recovers the 673 research forecast rows for version `v1`.
3. Recovers the 8 model-performance records for `v1`.

It checks the row counts and confirms that the expected research version is present. It also prints sample market and forecast records so you can see the recovered values.

### Why does this matter?

Suppose you restart your notebook kernel and lose variables such as `clean_nifty`, `evaluation`, or `forecast_matrix`.

Those variables no longer exist in memory. But if the required source data has been stored correctly in DuckDB, a new Python process can query the database and reconstruct the required DataFrames.

Notebook memory

Temporary variables disappear when the kernel restarts.

DuckDB database

Stored tables remain available to a fresh Python process.

One important distinction: Step 04 demonstrates recovery of these three stored datasets. It does not reconstruct every variable from every research notebook automatically. Any other variables must be recreated from their saved source data or by rerunning the relevant calculations.

Output: a terminal report confirming whether the three datasets can be recovered and whether their expected counts and research version match.

This is a small maintainability improvement we can consider later; there is no need to change it during this learning exercise.

# Part 2 — Understanding Steps 06–10

These five scripts move the project from stored research data toward a business decision.

## Step 06 — `06_prepare_business_inputs.py`

Builder

Purpose: Export the frozen research tables from DuckDB into files that can be used by downstream business analysis.

### What it reads

It opens DuckDB in read-only mode and queries two tables:

- `research_oos_forecasts`
- `research_model_performance`

It selects research version `v1` and orders the observations by date. Model-performance records are ordered by RMSE, from lowest to highest.

The script expects 673 out-of-sample observations, covering January 1, 2024 to September 22, 2026, and eight model-performance records.

### What it creates

It writes four artifacts to `data\business_inputs\v1`:

| Output                         | Purpose                                                                                    |
| ------------------------------ | ------------------------------------------------------------------------------------------ |
| `oos_forecasts.csv`            | Forecasts, actual volatility, NIFTY log returns and India VIX data                         |
| `model_performance.csv`        | MAE, RMSE, sample size and evaluation dates for each model                                 |
| `research_metadata.json`       | A copy of the authoritative research metadata                                              |
| `business_input_manifest.json` | Records the input source, row counts, dates and SHA-256 hashes of the three exported files |

The manifest helps detect changes to the exported files after they are created.

### Why it matters

DuckDB is the durable storage layer, while these CSVs are portable data artifacts that other tools can read.

One implementation detail: this script uses a hard-coded Windows project path. It also checks the expected row counts, dates, duplicate dates and missing values before exporting.

Important distinction: Step 06 does not retrain any volatility models. It exports existing research results.

## Step 07 — `07_validate_business_inputs.py`

Validator

Purpose: Check that the exported business-input files are valid and reconcile with their source data.

This is much more than checking whether the CSVs exist.

### What it checks

- Required files, columns and column order.
- Exactly 673 forecast rows and eight model-performance rows.
- Expected dates, chronological ordering and unique dates.
- Missing and non-finite numeric values.
- Model names, uniqueness and performance fields.
- Research version and manifest structure.
- SHA-256 hashes recorded in the business-input manifest.

The code performs field-level performance reconciliation, including MAE and RMSE comparisons within a small numeric tolerance.

### Why it matters

Imagine someone accidentally edits one forecast value in `oos_forecasts.csv`. The file might still have 673 rows and all the correct columns, but its contents would no longer match the recorded hash. Step 07 is designed to detect that change.

What a pass means: the exported files satisfy the script's defined data-quality and reconciliation rules. It does not prove that the original forecasting model is scientifically correct.

## Step 08 — `08_validate_frozen_research_outputs.py`

Research integrity validator

Purpose: Validate the authoritative, frozen research outputs themselves, rather than just the business-input copies.

Step 07 checks the business-input export. Step 08 checks the research-output contract.

From `data\research_outputs\v1`, it reads:

- `oos_forecasts.csv`

It does not mean that the models are permanently correct, that future forecasts will be accurate, or that the research can never be improved. A future revision should be versioned and validated separately rather than silently changing the current baseline.

## Step 09 — `09_prepare_business_decision_data.py`

Decision-policy builder

This is a major transition in the project. Instead of merely storing or validating forecasts, the script converts a forecast into a defined business action.

Purpose: Apply the frozen risk-regime and portfolio-exposure policy to the research observations.

### A. Which forecast does it use?

It reads the research data directly from DuckDB, selecting:

- Date
- NIFTY log return
- Actual volatility
- India VIX before the return
- `EGARCH_t_VIX`

It selects this forecast model explicitly rather than choosing the best model dynamically each day.

The script creates `Forecasted_Volatility` as a copy of `EGARCH_t_VIX`.

### B. How does it classify risk?

The script uses these frozen thresholds:

| Risk regime | Forecasted volatility condition |
| ----------- | ------------------------------- |
| Low         | At or below 0.004341            |
| Normal      | Above 0.004341, up to 0.005549  |
| Elevated    | Above 0.005549, up to 0.006882  |
| High        | Above 0.006882, up to 0.007676  |
| Extreme     | Above 0.007676                  |

For example, a forecast of `0.0060` is classified as Elevated because it is above the Normal threshold but below the Elevated upper threshold.

The thresholds are hard-coded in this script. Its comments and metadata state that they were calibrated using the development period only; this script applies and enforces the frozen values rather than recalculating the thresholds from scratch.

### C. How does the risk regime affect exposure?

The policy maps each regime to a portfolio exposure:

Low

### 100%

Normal

### 100%

Elevated

### 80%

High

### 60%

Extreme

### 40%

Illustration of the frozen policy's exposure levels; these are policy settings, not evidence of future performance.

In other words, the policy reduces exposure as forecast risk rises. Low and Normal regimes retain full exposure, while Extreme retains 40%.

### D. How does it protect the evaluation period?

The script divides the 673 observations into:

- Development: January 1, 2024–December 31, 2025; 495 observations.
- Evaluation: January 1, 2026–September 22, 2026; 178 observations.

It checks the counts and date boundaries. It also records that the evaluation period was not used for policy calibration.

This separation is important: if you tune the thresholds using the same period you later use to judge performance, you risk overstating how well the policy generalizes.

### E. What does it produce?

Under `data\business_decision\v1`, it writes:

- `business_decision_data.csv`
- `business_policy.json`
- `business_decision_manifest.json`

The CSV includes the source forecast, forecasted volatility, business period, risk regime and portfolio exposure. The JSON stores the frozen policy and metadata. The manifest records hashes and validation metadata.

The key idea: Step 09 turns a forecast into a reproducible decision rule. It does not prove that the chosen thresholds or exposure levels are economically optimal.

## Step 10 — `10_validate_business_decision_data.py`

Independent policy validator

Purpose: Independently reconstruct the decision labels and exposures, and check that the saved business-decision dataset matches its declared sources.

This script does not simply trust the risk regimes and exposures written by Step 09. It calculates what they should be and compares the reconstructed values with the saved values.

### What it checks

- Required files, schema, row counts and date range.
- Numeric integrity of the returns, volatility and exposure fields.
- The development/evaluation split: 495 and 178 observations.
- That `Forecasted_Volatility` matches `EGARCH_t_VIX`.
- That the policy JSON identifies the expected research version, forecast source and `FROZEN` policy status.
- That all thresholds and exposure mappings match the expected frozen values.
- That the risk regimes can be independently reconstructed from the forecast values.
- That each portfolio exposure matches the reconstructed regime.
- That the CSV and policy JSON hashes match the manifest.
- That the persisted decision dataset reconciles with the underlying DuckDB source.

It opens DuckDB read-only and does not modify the source research data.

### Why this is an important validation

Suppose a row has forecast volatility `0.0060`, but the saved risk regime says `Normal`. Step 10 would reconstruct the regime from the thresholds, find that the expected regime is Elevated, and fail the check.

Likewise, if an Elevated row were assigned 100% exposure instead of 80%, the independently reconstructed exposure check should detect the mismatch.

A successful Step 10 therefore supports the claim that the policy was applied consistently to the saved data. It does not prove that the policy itself is the best possible investment policy.

# Steps 11–12: Business evaluation

These two scripts are the point where your project moves from risk decisions to measured business outcomes.

- Step 11 — `11_evaluate_business_decision.py`: applies the frozen exposure policy to the evaluation-period NIFTY returns, calculates strategy metrics, and writes the results.
- Step 12 — `12_validate_business_evaluation.py`: independently recalculates key values and checks that Step 11's files, returns, metrics, and summaries are internally consistent.

## Step 11 — Calculate the business impact

### 1. Inputs and outputs

Inputs

`data/business_decision/v1/business_decision_data.csv`

`data/business_decision/v1/business_policy.json`

The CSV supplies dates, market log returns, risk regimes, and portfolio exposures. The JSON supplies the policy metadata, including its frozen status.

Outputs

`data/business_evaluation/v1/business_evaluation.csv`

`data/business_evaluation/v1/business_evaluation_summary.json`

The CSV contains daily calculations. The JSON stores aggregate performance metrics and a breakdown by risk regime.

Step 11 does not retrain the volatility models or discover new risk thresholds. It uses the prepared decisions and frozen policy to evaluate their historical outcomes.

### 2. What the script does, in order

1. Checks its inputs. Confirms that the two required files exist, the CSV has the expected columns, numeric values are finite, and the period labels agree with the dates.
2. Selects the evaluation period. Checks for 178 observations, the expected first and last dates, unique dates, and chronological order.
3. Checks the forecast and policy. Confirms that the selected forecast is `EGARCH_t_VIX`, that the forecast column matches that source, and that exposures match the frozen mapping. It also checks that the evaluation period was not marked as used for policy calibration.
4. Calculates daily returns. Compares full market exposure with the policy-driven adaptive exposure.
5. Builds wealth series. Compounds each strategy's daily returns to track the value of an initial unit of capital.
6. Calculates performance metrics. Measures returns, drawdown, volatility, downside deviation, Sharpe ratio, exposure reduction, and other comparisons.
7. Breaks results down by regime. Summarizes observations, average forecast volatility, average exposure, and return differences in each risk regime.
8. Writes the CSV and JSON. These files become the evidence used by Step 12 and the later reporting scripts.

### 3. The return calculations — an important detail

The script uses logarithmic market returns as its input. It calculates static market return as:

\\[ R\_{\text{static}}=e^r-1 \\]

For the adaptive strategy, it first multiplies the log return \\(r\\) by the policy's exposure \\(w\\), then converts the result into a simple return:

\\[ r\_{\text{adaptive}}=w r \\]

\\[ R\_{\text{adaptive}}=e^{wr}-1 \\]

Here, \\(w\\) is the portfolio exposure: 1.0 means 100%, 0.8 means 80%, 0.6 means 60%, and 0.4 means 40%.

Example: if the daily log return were \\(-2\\%\\) and exposure were 40%, the script would calculate the adaptive simple return as \\(e^{-0.008}-1\\), approximately \\(-0.797\\%\\).

This matches the actual source code. But there is a financial-methodology decision to resolve before calling the results final.

If the intention is a conventional portfolio that invests fraction \\(w\\) in the index and holds the remainder in cash earning zero, the usual daily simple-return calculation is:

\\[ R\_{\text{portfolio}}=w(e^r-1) \\]

That differs from the script's \\(e^{wr}-1\\). Neither formula should be substituted silently: the correct choice depends on what the exposure is intended to represent. Step 12 currently checks that the implementation matches the chosen formula; it does not determine which financial interpretation is appropriate.

### 4. What performance metrics does Step 11 calculate?

| Metric                         | What it tells you                                                                                            |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| Arithmetic return              | Sum of daily simple returns; useful as a descriptive measure, but not the compounded investment result.      |
| Compounded return              | The result of compounding the daily returns over the evaluation period.                                      |
| Terminal wealth                | The ending value of one initial unit of capital.                                                             |
| Maximum drawdown               | The largest peak-to-trough decline in the wealth series.                                                     |
| Annualized volatility          | How variable daily returns are, scaled to a 252-trading-day year.                                            |
| Downside deviation             | Annualized variability of returns below the zero-return target.                                              |
| Sharpe ratio                   | Average excess return relative to return variability; Step 11 uses a zero annual risk-free rate by default.  |
| Average exposure reduction     | One minus average portfolio exposure.                                                                        |
| High/Extreme regime statistics | How often the policy classified risk as High or Extreme, and the average exposure during those observations. |

It also calculates negative-return observation counts and the sum of negative daily returns. These are descriptive statistics, not a substitute for examining the full loss distribution.

Important distinction: a better result relative to the static strategy does not necessarily mean the adaptive strategy made money. A strategy can lose less than the benchmark and still have a negative total return.

## Step 12 — Independently validate the evaluation

Step 12 is designed as a read-only validator. It reads the decision data, policy, evaluation CSV, and summary JSON; it should not modify those files.

### 1. What it checks

1. File and schema checks: all four required files exist, and the evaluation CSV contains the expected columns.
2. Period checks: the evaluation has 178 rows, covers the expected dates, is chronological, and has no duplicate dates.
3. Source reconciliation: daily source values, risk regimes, exposures, and dates match the evaluation-period records in the decision dataset.
4. Numeric integrity: required numeric columns contain no missing, non-numeric, or infinite values; exposure remains between 0 and 1, and static exposure remains 1.
5. Frozen policy checks: the policy status is `FROZEN`, the forecast source and exposure mapping are correct, and the evaluation period is not marked as used for calibration.
6. Return reconciliation: recalculates static returns, adaptive log returns, adaptive simple returns, and daily protection benefit from the source data.
7. Wealth reconciliation: independently compounds daily returns and checks both wealth series.
8. Summary metric checks: recalculates key performance measures and compares them with the saved JSON summary.
9. Regime-summary checks: rebuilds the risk-regime summary from the daily evaluation data and compares it with the saved summary.
10. Traceability: prints SHA-256 hashes for the current input and output files, helping identify exact file versions.

### 2. What does a PASS actually prove?

A PASS is meaningful, but its scope needs to be clear.

- It supports that the files agree with one another and that the calculations follow the formulas encoded in the scripts.
- It supports that the saved summary can be reconciled with the daily evaluation records.
- It does not prove that the exposure policy is economically optimal, that the model will work in the future, or that the return formula represents the intended real-world portfolio.
- The printed hashes provide identifiers for the current files. By themselves, they do not prove that the files are correct or unchanged from an earlier run unless compared with a trusted prior hash.

178 daily records per scenario = 1,068 output rows in total.

### 3. How the script calculates turnover

The code treats the initial position as cash with zero index exposure.

For the first observation:

\\[ T_1=|w_1-0| \\]

For subsequent observations:

\\[ T_t=|w_t-w\_{t-1}| \\]

It also adds final liquidation turnover equal to the last exposure. Here, \\(w_t\\) represents the target exposure and \\(T_t\\) is the turnover proxy.

For example, a move from 100% exposure to 60% exposure gives a target-exposure change of 40 percentage points, or turnover of 0.40 under this convention.

This is a simplified calculation based on changes in target exposure. It is not execution-level turnover and does not track all changes in portfolio weights caused by market movements between rebalances.

### 4. How transaction costs are applied

The script calculates the cost fraction as:

\\[ C_t=T_t\frac{\text{cost bps}}{10{,}000} \\]

Then it calculates net return using:

\\[ R\_{\text{net},t} =(1+R\_{\text{gross},t})(1-C_t)-1 \\]

In plain English, it applies the gross investment return and then deducts the modeled transaction-cost fraction multiplicatively.

The gross return formula is the same one used in Step 11:

\\[ R\_{\text{adaptive},t}=e^{w_t r_t}-1 \\]

So Step 13 preserves the earlier return convention; it does not resolve the portfolio-weighting question discussed in Step 11.

### 5. What the script measures

For every strategy/cost combination, it calculates:

- Compounded return and ending wealth
- Annualized volatility and Sharpe ratio
- Annualized downside deviation
- Maximum drawdown
- Number of negative-return days
- Total one-way turnover and summed cost fractions
- Mean daily exposure

It then compares Adaptive against Static at each cost level, including differences in compounded return, drawdown and volatility.

The JSON also records input-file SHA-256 hashes and explicitly documents limitations: no separate modeling of bid–ask spread, market impact, taxes, financing or operational constraints.

What Step 13 can tell you: how results change under the script's stated cost assumptions and turnover convention. It cannot establish actual trading profitability or real-world implementation costs.

### Validation sequence

3. Dates and source records: checks that evaluation dates match the decision source and that no dates are missing, duplicated or unexpected.
